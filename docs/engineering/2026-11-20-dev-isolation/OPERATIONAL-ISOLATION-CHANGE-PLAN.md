## Decision in front of the owner

The new standard DEV identity cannot safely be activated merely by creating a separate folder on H:. Production source has a shared, mutable ancestor chain; the production runtime/state child ACLs alone are not a demonstrated namespace boundary. The design must first provide a **protected production code/control/trust root that a real DEV token cannot mutate or replace**, plus an independently protected DEV root.

**Preferred candidate for explicit review (Option A, strengthened by a three-sibling inherited-rights inventory):** preserve the running production instance on H: until a separately qualified, rollback-capable cutover can move production code and authority/trust state into administrator-controlled, explicitly ACL-protected roots on C:. Then allocate a *different* protected DEV code/data root, standard DEV account/profile, and DEV-only downstream resources. Merely copying files, changing a shortcut, or adding a directory is **not** a qualified cutover.

**Alternative requiring substantially more review (Option B):** scoped hardening of the H: ancestor hierarchy, including the H: root-to-MTechLabs namespace and all affected siblings, if a complete access check proves that legitimate unrelated workloads remain safe. **Do not blanket-reset H: or assume hardening only H:\MTechLabs\MCP protects its name from its parent.** Option B is *not* selected.

No choice is authorized by this document. The owner must approve an exact, complete future change set after hosted source acceptance and protected-backup/rollback review.

## 4. Cutover controls and emergency rollback to design in advance

- Preserve the old owner-managed production service/shortcut and source/state as **read-only historical evidence and a qualified fallback**, without granting DEV access to the broad H: namespace. The original H: installation is **not automatically a safe long-term rollback target** given its unresolved parent rights.
- Record before/after exact process owner, binary/entry/config identity, PID and creation time, bound listener address, current startup authority, endpoint reachability and signed reference outcomes. Avoid displaying raw command lines or tokens.
- Define an explicit quiescence/drain policy for existing requests: prevent new work, wait for tracked operations, report unknown outcomes, then switch only the verified owner-managed process. Do not assume closing a terminal kills an existing detached child.
- Track only **newly allocated** DEV credentials, routes, keys, apps and grants for reversal; a DEV failure must never trigger alteration of production Cloudflare, Access or the existing staging gateway.
- Restoration must be based on an independently verified protected backup or approved exact prior deployment, plus saved ACL/ownership and sign-in shortcut metadata. Record what is not reversible (in-flight work or remote grant state) rather than claiming instant zero-risk rollback.
- Any failure in parent namespace ACL, new root ownership, native account evidence, startup reconstruction, original production availability, protected key authority or source hash means **stop, preserve evidence, and do not proceed to the next stage**.
